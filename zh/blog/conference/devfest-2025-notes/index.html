DevFest 2025 筆記：AI Agent 時代的開發者進化論

Created on December 01, 2025

2025   ·   DevFest 2025   AI Agents   Gemini   Google ADK   MCP   Software Engineering   Developer Tools   ·   Conference

前言

前陣子參加了 DevFest 2025，今年的主題無疑圍繞著 AI Agent 與 Agentic Workflow。從單純的 Prompt Engineering 到讓 AI 擁有「手腳」去執行任務，整個軟體開發的典範正在發生巨大的轉變。

這次的議程非常豐富，從獨立開發者的實戰經驗，到 Google 官方工具鏈 (Gemini CLI, ADK) 的深度解析，再到企業級的應用架構。我整理了每個 Session 的重點筆記，記錄下這場知識饗宴的精華，也希望能幫助沒能到場的朋友們一窺 AI Agent 時代的樣貌。

1. 宅宅自以為的浪漫：跟 AI 一起為自己辦的研討會寫一個售票系統

講者：高見龍 (Amos)

這場分享讓我印象深刻，高見龍老師分享了他如何從「宅宅自以為的浪漫」出發，用 AI 輔助自己打造一套功能完整的售票與銷售系統 ezBundle。

重點在於，AI 雖然強大，但最終還是工程師意志的延伸，基本功才是王道。

為什麼要自幹一個售票系統？

雖然市面上不乏優秀的 K 牌或 A 牌報名系統，但講者遇到了一些無法解決的痛點：

  • 客製化彈性不足：現有平台對於細節客製化難度較高。
  • 現金流需求：辦活動常需先支付高額場地費（例如 2025 WebConf 的場地費高達百萬台幣），既有平台通常在活動結束後才能撥款，造成主辦方極大的現金流壓力。
  • 「解決自己的問題，可能也解決了別人的問題」：ezBundle 的目標並非取代大牌系統，而是解決自己辦活動時遇到的實際問題。

AI 協作的真實生產力

ezBundle 系統證明了 AI 寫的程式碼已經可以投入生產環境：

  • 單兵作戰的驚人成果：此專案由 1 位工程師（無 PM、無設計師）利用下班和週末時間完成。
  • 效率極大化：整個專案程式碼量約 29 萬行。講者評估，他自己可能只寫了不到 1% 的程式碼。
  • 營運實績：自 2025/9/1 上線以來，會員數超過 1,000 人，成交金額已接近 NT$ 290 萬。
  • 功能涵蓋廣泛：系統不僅能賣票，還能銷售實體商品、數位內容，並整合多元支付（藍新、綠界、LinePay）、QR Code 票券驗證、問卷與簽到功能。

如何讓 AI 「乖乖」聽話：開發流程實戰

使用 AI 輔助開發，最大的挑戰在於如何控制品質，避免產生「科技垃圾」(Tech Garbage)。

(A) 善用 CLI 與 Pipe

  • AI 不應被編輯器綁架：CLI (Command-Line Interface) 工具可以讓 AI 在伺服器上也能運作，並且提供了極大的彈性。
  • Pipe 概念：將不同 AI 模型串接起來，讓前一個模型的輸出成為下一個模型的輸入。例如：先請 Gemini 找出潛在問題，再請 Claude 提供修復建議並修改程式碼。

(B) 掌握規格與設計

  • 避免 Vibe Coding：許願不等於做出可用的東西。要讓 AI 產出穩定且符合預期的結果，必須提供明確的依據。
  • Few-Shot/One-Shot 範例：為了確保畫面風格一致，利用 One Shot 或 Few Shot 的方式，給予 AI 參考範例（例如 ViewComponent 預覽）讓它去「抄作業」，確保設計遵循 Design Guidelines。
  • TDD (測試驅動開發)：這是確保系統核心功能（如結帳）不出問題的關鍵。即使是 AI 寫的程式碼，也必須通過測試的驗證。

(C) 嚴守主控權

  • AI 是協作夥伴，不是決策者：對於 AI 產出的程式碼，工程師仍需進行 Code Review。
  • 掌握 Git 權限：絕對不要讓 AI 代替你操作 Git。雖然可以使用 git auto-commit 讓 AI 幫忙生成 Commit Message，但最終的權限（包括安裝套件的權限）仍需掌握在自己手上。
  • 錯誤監控：利用 Sentry 等工具進行監控，一旦發生錯誤立即發出通知。這比使用者回報才發現問題要及時得多。
NOTE

結論：AI 是能力放大器

工程師不會被 AI 取代，但角色會發生變化。

  • AI 是駕駛員意志的延伸：只要工程師本身技術夠強，AI 就能將你的能力放大好幾倍。
  • 練好基本功：AI 會放大你的好習慣，也會放大你的壞習慣。在 AI 時代，基本功變得更重要，必須「人要比車兇」。
  • 角色轉變：工程師將從「程式碼生產者」轉變為「程式碼審核者」、「架構師 + 產品思考者」。

2. 利用 Gemini CLI 與 ADK 開發 Agentic 應用

講者：Jimmy Liao (AI GDE, CTO & Co-Founder)

這場 Session 的核心在於如何利用 Google 的 Agentic 技術堆棧，解決企業導入 AI 時遇到的痛點，並提供從快速驗證到正式部署的實戰路徑。

企業導入 AI 的三大痛點 💥

  1. 資料安全疑慮 (Data Security)：敏感資料不能上傳到外部 API，需要本地部署或資料掌控權高的解決方案。
  2. 工具整合困難 (Tool Integration)：內部系統（如 Jira、GitLab、內部 API）各自為政，缺乏統一的整合標準。
  3. 開發者體驗差 (DevX)：存在多個 AI 介面（CLI、Web UI、API），造成開發混亂。

核心技術堆棧 (Core Tech Stack)

為了解決上述痛點，解決方案基於三個核心組件：

組件名稱 定位/作用 備註
Gemini CLI 快速驗證與迭代 Google 官方命令列工具，支援最新 Gemini 模型，提供免費額度 (50 req/min)，適用於第一階段的快速試錯。
MCP Protocol 標準化工具整合 (Model Context Protocol) 類似 LLM 與外部工具之間的「USB 協定」，任何工具只需實作一次即可被多個 Client 呼叫。
Google ADK Agent 自動化編排 (Agent Development Kit) 專為 Agent-first 架構設計，原生支援 MCP，強項在於多步驟工具的自動編排和上下文記憶。

實戰 Demo 與效益亮點 ✨

  • FastMCP 台股查詢：使用 FastMCP (僅 50 行程式碼) 快速將證交所 API 包裝成 MCP Server。將手動查詢時間從 5-10 分鐘縮短至 5 秒內。
  • 企業文檔合規檢查：實作 Document MCP，自動掃描文件中的敏感資料（如個資），將 3-5 天的人工稽核縮短至 5 秒。
  • Google ADK 投資分析：結合多個 MCP Tools，透過 ADK Agent 進行自動推理和完整投資分析，效率提升驚人。
TIP

實用比喻

整個企業 Agentic 開發流程，很像是在建立一個企業內部的超級工具箱：

  • MCP 就像是統一的電源插座規格 (USB 協定)，確保你公司的所有工具（GitLab、Jira）都能用標準化的方式與 AI 模型對接。
  • Google ADK 則扮演高級技師的角色，它能根據你的語音指令，自動判斷需要拿起哪些工具，並精確地按照順序完成複雜的任務。

3. ADK/A2A/MCP 實戰解析

講者：Edward Chuang

這場議程深入探討了 AG (Agent) 時代的架構設計。Agent 的核心組成包含：Runtime (R)、Model (腦力) 以及 Tools (手腳)。

ADK：Google 的 Agent 開發框架

ADK (Agent Development Kit) 是 Google 推出的開源框架，支援單一代理人 (Single Agent) 和 多代理人 (M-Agent) 架構。

Tools（工具）的類型： Agent 會根據使用者請求 (Prompt) 和自身指示 (Instruction)，決定呼叫哪個工具：

  1. Function Tool：使用者自定義的函式。
  2. Building Tool：ADK 內建工具（如 Google Search）。
  3. Third-Party Tool / MCP Tool：整合外部服務，如 GitHub API。

🧠 Agent 的架構模式 (Patterns)

1. Single Agent (單一代理人) 一個 Agent 負責判斷並調用它擁有的多個工具。優點是結構簡單、延遲低；缺點是難以處理複雜 Workflow。

2. Multi-Agent (多代理人) 透過 協調者 (Coordinator/Root Agent) 將任務分配給多個 Sub-Agent。

  • Dispatcher / Coordinator：Root Agent 決定流程，模組化高。
  • Sequential (串聯)：預先定義固定順序 (A -> B)。結果可預測，但延遲會疊加。
  • Parallel (並行)：多個 Agent 同時執行。效率高，但複雜度增加，Debug 較困難。

A2A (Agent-to-Agent) 協定 這是 Agent 之間的「名片」，讓一個 Agent 能夠發現並理解其他 Agent 的能力與溝通方式。

WARNING

挑戰與建議

Agent 系統的主要挑戰在於 可預測性 (Predictability) 和 穩定性 (Stability)。 建議從最簡單的架構（Single Agent）開始，不要一開始就過度設計複雜的 M-Agent Pattern。

4. 使用 Gemini CLI 打造無程式碼的 AI Agent 代理人

講者：Will 保哥

誰說玩 AI Agent 一定要寫 SDK 串 API？這場議程展示了如何利用 Gemini CLI 把複雜的 AI 應用轉化為業務設計任務。

Gemini CLI 的核心定位

Gemini CLI 讓使用者無需編寫程式碼，即可透過終端機直接與模型互動。

  • 簡化開發：大幅降低技術門檻，專注於 Agent 設計。
  • 快速原型：幾分鐘內就能建立可互動的原型。

Agent 實戰心法：工具、角色、測試

建立 AI Agent 的三大要素：

  1. 註冊外部工具 (Tools) 要讓 Agent 擁有「超能力」，核心在於工具呼叫。將本地腳本 (如 Shell Script) 註冊為 Gemini CLI 可呼叫的工具。 心法：遵循單一職責原則，將複雜執行細節外包給獨立 CLI 工具，讓 LLM 專注於邏輯控制。

  2. 角色設定與提示詞 (Prompt) 優化 高品質 Agent 仰賴精確的 System Prompt：

    • 角色定義 (Persona)
    • 任務指令 (Task)
    • 行為邊界 (Constraints)

  3. 測試與迭代 不要試圖用一個超長的 Prompt 完成所有事。應分段進行，將複雜流程拆解成多個單一功能的節點。

5. 透過 Google ADK 和 Gemini CLI 來打造人類與 AI Agent 團隊協同工作模式

講者：Simon Liu

這場議程展示了 人類與 Agent 團隊 的協同工作模式。架構設計遵循「大模型做大事，小模型做小事」的原則。

架構規劃

  • Gemini CLI / Main Agent：主要的協調者，接收使用者指令並進行宏觀規劃。
  • Google ADK Agents / Sub Agents：專業的子代理，執行特定任務。
  • Gemini CLI Extension (adk-agent-extension)：串接兩者的橋樑。使用者透過 CLI 下令，Main Agent 透過 Extension 呼叫遠端的 ADK Agent。

實際應用案例

  • HR Agent：協助 HR 整理員工入職流程 (Onboarding)，由 Hiring、Salary、Performance 等多個子 Agent 協同運作。
  • Database Agent：準確撈取資料庫 (DuckDB/PostgreSQL) 資料。透過自然語言查詢數據趨勢，Agent 自動執行 SQL 並返回結果。
  • PM Agent：撰寫 PRD 並協同繪圖 Agent (Nano extension) 生成架構圖。

6. The MCP Workshop: Turning APIs into AI-Ready Tools

講者：Tamas

這場 Workshop 非常有趣，Tamas 一開始為了幫大家提神，還帶大家全體起立做運動。他叫大家舉起雙手快速碰掌，正當大家認真跟著做時，他突然拿出手機轉身跟大家自拍，這突如其來的舉動真的滿好笑的，瞬間讓現場氣氛熱絡起來。

在輕鬆的開場後，Tamas 由淺入深、一步一步帶著大家實作，手把手教學如何打造一個標準的 MCP Server。

(內容主要為實作環節，重點在於體驗如何將既有的 API 轉化為 MCP Server，讓 AI 能夠理解並使用這些 API。)

總結

參加完 DevFest 2025，最深的感觸是：工程師的角色正在快速演化。

我們不再只是「寫程式的人」(Coder)，而是正在轉變為「AI 協調者」與「架構師」。工具如 Gemini CLI、Google ADK 和 MCP 協議，正在為這個新時代鋪路。

未來的開發模式，將是人類定義目標，AI Agent 團隊協同執行。而我們的核心價值，將取決於我們如何設計這些 Agent、如何定義它們的溝通方式，以及如何確保它們產出的品質與安全。

這是一個令人興奮的時代，讓我們一起擁抱變化，與 AI 共舞！
